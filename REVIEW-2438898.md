## What is right, and worth saying plainly

- **`SCRIPT_HELD` as a falsy float subclass.** I probed it rather than taking it:
  `bool()` False, `is not False`, `is isinstance float`, `is not bool`. The
  hazard I expected — equal-to-`False` comparisons — is real (`SCRIPT_HELD ==
  False` is `True`, and `hash` collides with `hash(False)`), but the only
  consumer in the file is `if self._run_script_tick():` at `:3082`, a bare
  truthiness test, and there is exactly one return site (`:2880`). Every test
  uses `assertIs`. So identity is the only thing anyone does with it, and the
  design is safe **as used**. It is a sharp tool: any future `== False` or
  `in (False,)` breaks it silently. Worth a comment at `:3082`, not a change.
- **The `:1419` ImportError path** now reports FAILED and releases the hold —
  exactly the "every generation-consuming path terminates" fix, and it lands
  before the publication of `_orch_cancel`, which was the stranding window.
- **The pivot.** Keying on a generation counter and returning `False` were both
  wrong, and the builder found that themselves, by tightening a test to assert
  the hold *itself* was released rather than a proxy. That is the correct
  diagnosis of their own bug and the right instinct to report rather than bury.
- `_end_script_hold` rejects empty `goal_id`, so the spec-driven and
  order-worker paths release nothing. Correct, and tested.

## F1 — two different goals get the same `goal_id`, so a finished goal releases a live goal's hold

Both accept sites build the identity the same way:

```python
_goal_id = f"chat:{sender}:{text[:40]}"     # agent.py:669 and :872
```

`text[:40]` is not an identity. Two genuinely different goals that share a
40-character prefix collapse to one id:

```
chat:Steve:mine ten oak logs and then craft a table   <- "…now"
chat:Steve:mine ten oak logs and then craft a table   <- "…first"
```

Then, in order:

1. goal A accepted → `_begin_script_hold(A)`; A owns the hold
2. goal B accepted → `_begin_script_hold(B)`; B *replaces* A as owner
   (correct — last accepted owns the hold)
3. **A finishes first** → A's `finally` at `:1565` calls
   `_end_script_hold(A)` → `hold["goal_id"] == A` is `True` because it is the
   same string → **B's hold is released while B is still running**

The script then resumes into a goal the planner still owns. That is the
double-issue this entire requirement exists to prevent, arriving through the
identity mechanism the requirement was written to guarantee.

Proven by driving the **real** `BotRunner._begin_script_hold` /
`_end_script_hold` (builder's own module bootstrap, no stubs of those methods):

```
[Scout/hold] script held by goal 'chat:Steve:…craft a table'
[Scout/hold] script held by goal 'chat:Steve:…craft a table' (replacing '…craft a table')
[Scout/hold] released 'chat:Steve:…craft a table'; the script resumes
AssertionError: True is not false : REAL _end_script_hold let a finished goal
release B's live hold
```

**Control** (distinct ids `goal-A` / `goal-B`): `end(A)` returns False, hold
survives as `goal-B`, `end(B)` releases. So the ownership logic is correct and
the defect is entirely in the id construction — not in the hold machinery.

**Suggested fix**, builder's choice: make the id unique per goal rather than
prefix-derived — a monotonic counter or `uuid4` at the accept site, keeping
`chat:{sender}:` only as the human-readable `goal_text`. The spec already says
"identify the goal that owns the hold"; a truncated chat prefix does not.

## F2 — no test builds an id the way the code does

Every test in `ScriptHoldTest` hand-passes a literal: `"goal-A"`, `"goal-B"`,
`""`. Not one goes through `f"chat:{sender}:{text[:40]}"`. So
`test_only_the_owning_goal_releases_the_hold` passes on ids that are trivially
distinct and can never catch F1. This is a fixture-shape gap, not a missing
assertion: the assertion is right, the input cannot exhibit the defect.

A test that constructs two ids through the production expression and asserts
they differ would redden on the current code.
