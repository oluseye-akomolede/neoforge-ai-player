## F1 (my finding at `b62293c`): WITHDRAWN — the lead was right

I filed F1 as "a refused bind releases the hold only on success; the steps then run
while the hold blocks the script." That was wrong, and I checked the premise before
conceding rather than deferring:

- `_run_script_tick` gates on `_script_hold` alone (`agent.py:2966-2967`) — it returns
  `SCRIPT_HELD` for whatever `_get_script_tick()` produced, planner or hand-written.
- `_bind_planner_script`'s docstring states it: a `False` return *leaves the bot exactly
  as it was: any previously bound script stays in force.*

So on a refused bind the script that is held is the **pre-existing hand-written one**,
and the refusal happened *because* it is deployed. Releasing the hold there would resume
that script while the planner's steps run — the two-driver bug M3-1g exists to prevent.
`cc3b468` restored the unconditional hold; `:1612-1614` releases only on a successful
handover, while the terminal paths still release at `:1469` and `:1601`.

**How I got it wrong:** I applied "release only on success" as a mutant, it reddened the
test I had just written, and I read a red test as proof of an invariant. It only proved my
assertion encoded what I wrote into it. The `b62293c` review now carries a forward pointer
to this one.
