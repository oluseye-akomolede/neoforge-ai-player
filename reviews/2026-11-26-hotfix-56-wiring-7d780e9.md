## F-2 is closed, and the Java test is the better record

The corrected commit message no longer says `record()` refuses a null. Line 44 mentions
"making record() refuse a null" only as the **mutant**, which is accurate.

The new `toleratesANullPreviousCodeHoursAsAbsence` pins three things, not one:
`record()` returns true for a null, `get().previousCodeHours()` is null, and `toJson()` does not
echo `previous_code_hours` back. That third assertion is the one that matters — it says a null is
*stored as absent*, which is the receiver behaviour a future sender change must stay safe against.

My mutant made `record()` refuse a null (the old message's claim):

```
ScriptReportStoreTest > toleratesANullPreviousCodeHoursAsAbsence() FAILED
tests=15 failures=1 errors=0
```

One red, the intended test, nothing else. Restored byte-identical to the archive
(`ScriptReportStore.java` md5 `78e31f0e…`, matching `git show 7d780e9:…`).

### Answer to question (c): the test is better than a corrected sentence, and you should keep both kinds

A sentence in a commit message records what someone *believed* at one moment and is not
executed again. The Java test asserts what the receiver *does* on every run, and it reddened on
the plausible mutant. That is strictly more durable.

But note the scope the added test leaves: I grepped the spec and tasks at `7d780e9` —
**neither ever carried the false claim**, so there was nothing there to correct. The spec is
silent on null-vs-absent for this field. That silence is itself a small gap: the spec says the
field is "absent unless LOWER", which describes the *sender*, and says nothing about what the
receiver does if a sender ever nulls it. The Java test now covers the receiver; the spec still
does not state it. That is acceptable — the test is the contract for receiver behaviour, and the
spec's concern is the payload the sender emits — but if a future change ever touches
`build_body`, the only guard is the Java test, which lives one repo-layer away from the Python
sender. That is worth knowing, not worth blocking on.
