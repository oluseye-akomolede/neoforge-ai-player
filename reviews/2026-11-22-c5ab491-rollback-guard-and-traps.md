# c5ab491: rollback refuses a None-valued password; every credential temp file trapped — PASS

Rev reviewed: `c5ab491`. Reviewer: minecraft-reviewer@minecraft. 2026-11-22.
Closes D-1 and the `/tmp/prod.b64` leak filed against `9c885cf`.

## Verdict

PASS. The guard rejects the value rather than its absence, and the trap is load-bearing
— I proved both by running the plan's own blocks, and by running the same block with the
trap deleted to show it leaks without it.

## What the defect was

`urlsplit(...).password` returns `None` when userinfo is absent, and `print(None)`
renders the **four-character string** `None`. So a garbled or empty backup produced
`OLD=None`, which is non-empty and passed the previous `[ -n "$OLD" ]` guard. The
rollback would then run `ALTER ROLE aibot PASSWORD 'None'`, which SUCCEEDS — setting the
role to a value no consumer holds, in the one section whose purpose is to restore a
working credential. It failed open. A corrupt backup was worse than no backup.

## Guard: run against the bad inputs, per the lead's request

Extracted the rollback block from `c5ab491` (`git show c5ab491:…` → the block, then its
`REMOTE` body) and ran it with a `kubectl` stub that logs every invocation. The log is
the measurement: the ALTER is visible iff the block reaches `exec deploy/pgvector`.

| input | parse | rc | ALTER sent | `/tmp/pgdsn.rb` |
|---|---|---|---|---|
| `not-a-dsn` | `None` (len 4) | 1 | **0** | gone |
| empty file | `None` (len 4) | 1 | **0** | gone |
| `postgresql://aibot:@h/d` | `""` (len 0) | 1 | **0** | gone |
| `postgresql://aibot:pa'ss@h/d` | `pa'ss` | 1 | **0** | gone |
| `…aibot:0123…cdef@h/d` (32 char) | 32-char value | 0 | **1** | gone |

Refused **before any ALTER** in every bad case, as required. Both interpolation sites
carry the guard (4b rehearsal and the rollback); I drove 4b separately and it likewise
sends no ALTER on a garbled DSN.

## Trap: proved load-bearing, not incidental

The prod restore writes `/tmp/prod.b64` (prod's base64 PG_DSN), then `patch`es under
`set -eu`, then `rm`s. A failing `patch` exits at the `patch`, so the `rm` never runs.

- **With the trap** (`p2.sh` as committed, stub `patch` forced to exit 1): rc=1,
  `patch` attempted once, `/tmp/prod.b64` **gone**.
- **Without the trap** (same block, `trap` line deleted): rc=1, `patch` attempted once,
  `/tmp/prod.b64` **LEFT ON DISK**, contents decoding to
  `postgresql://aibot:…@pgvector`.

That control is the point: the trap is what removes the credential, not the surrounding
control flow.

## Not established

- Nothing here was run against the cluster. The `kubectl` is a stub; the confinement
  claim (that these run on controlplane under `ssh … bash -s`) is read from the plan's

- The guard assumes the new password is hex (generated by the plan), so the quote branch
  is defensive for a legacy value. It is correct, not exercised by the real generator.
