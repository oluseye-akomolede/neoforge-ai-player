## The guard works

Probed `_normalise_query_result("blocks", ...)` across nine shapes:

| input | ok | reason | matches | `blocks` present |
|---|---|---|---|---|
| `{blocks:[], error:"boom"}` | False | error | `[]` | no |
| `{blocks:[{x:1}], error:"boom"}` | False | error | `[{x:1}]` | no |
| `{blocks:[{x:1}], error:""}` | True | – | `[{x:1}]` | no |
| `{blocks:[{x:1}]}` | True | – | `[{x:1}]` | no |
| `{blocks:[]}` | True | – | `[]` | no |
| `{blocks:[], error:None}` | True | – | `[]` | no |
| `{blocks:[], error:"boom", reason:"custom"}` | False | **custom** | `[]` | no |

The two that matter most and that reasoning alone would have got wrong: `error:""` stays a
success (an empty string is not a failure), and a mod-supplied `reason` survives, because
the guard uses `setdefault` rather than assignment. The guard also sits *after* the list
rename and *before* `setdefault("ok", True)`, which is the only ordering that works.

## F-1: the `surface_scan` justification is false — `:1420` is `scan_data`

The commit message, the docstring, the row body and **my own previous review** all say
`surface_scan` sends `{blocks, count, error}` today at `HttpApiServer:1420`. It does not.
Measured at `9a8a083`:

- `:1425` is `case "surface_scan"`, and it completes `Map.of("blocks", blocks, "dimension",
  dim)` — **no error key, and no try/catch of its own**. An exception falls to the outer
  handler.
- `:1420` is inside `scan_data`, which is what sends `{blocks, count, error}`.

I raised O-1 with the statement "`surface_scan` already does the right thing at `:1420`",
inherited it from the builder's row without opening the Java, and it propagated into my
committed review and my message to the lead. That is the failure my own notes name as
"a justification must cite its own class", and I am correcting it here rather than
leaving a stale claim in the record.

**Stronger still:** neither verb is reachable as a declared query. `_QUERY_KEYS` allows
exactly four kinds — `blocks`, `entities`, `block_at`, `locate`. `scan_data` and
`surface_scan` are not among them, so the "this shape arrives today" half of the
justification is false regardless of the line number.

## Does that make the guard wrong?

**No, and this is the important distinction.** The guard protects a shape that is
**unreachable today** and **will be reachable the day O-1 is fixed**, if `find_blocks`
gains an error key the way `scan_data` has one. Building it now is cheap; discovering the
normaliser reports `ok:true` on a failed search, after the Java change has shipped, is
what the builder's own argument calls a silent wrong answer. Keeping it is right.

But the *reason given* for it must be right, because a future reader will check `:1420`,
find `scan_data`, and conclude the whole guard is speculative. The docstring should say:
no query kind sends an error key today; `scan_data` is the shape a fixed `find_blocks`
should copy; this guard makes that fix safe to land. The commit message cannot be amended,
so this review is the forward pointer.

## F-2: `ok:false` with no `error` key still yields `reason=None`

Measured: `{blocks:[], ok:false}` → `ok=False, reason=None`. A script sees a failure with
no explanation. Narrow, and I checked reachability before rating it: every `ok:false` the
mod emits pairs with `"error"` (`:677, 696, 699, 714, 722, 724, 757, 763, 796, 835, 843,
845`), and the query verbs emit no `ok` at all. So this is not reachable through any
declared query today — I record it as a property of the normaliser to know about, not a
defect to fix now. If the mod ever sends a bare `ok:false`, the failure will arrive with
no reason.
