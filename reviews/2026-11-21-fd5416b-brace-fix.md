## The structural fix, verified rather than read

The builder's claim is "drift is now impossible by construction". I tested the
construction three ways:

1. **One constant, two renderers.** `planner.py:33` defines
   `_SCRIPT_SURFACE_SLOT = "@@SCRIPT_SURFACE@@"`; the constant is substituted
   AFTER `.format` via `.replace` (`planner.py:211-214`), so it never enters the
   format engine. `l3_planner.py:1619` passes it as a value into
   `_SCRIPT_SYSTEM_PROMPT.format`, whose braces are all format fields — a
   different mechanism, correct for each template. `call_script:1638` and
   `decompose`'s caller use these two renderers, so production and tests share
   one path per prompt.

2. **Drift canary.** I inserted `DRIFT-CANARY` once inside `SCRIPT_SURFACE` and
   rendered both prompts: present in legacy **and** L3. A single edit reaches
   both texts. That is the construction claim, executed.

3. **The bug cannot come back silently.** M6 re-introduced doubled braces on
   `{ok, seq}` (the exact shipped bug) → `FAILED (failures=2)`:
   `test_the_rendered_prompt_has_no_doubled_braces` and
   `test_the_l3_script_prompt_has_no_doubled_braces`. Both prompts are gated.

## Spec

The scenario at `spec.md:229` requires the rendered prompt to name
`look.blocks(...)` etc. "with the arguments and the return shape
(`{ ok, matches }`, or `{ ok: false, reason }`)". Single braces are the only
form that satisfies it, so the spec does gate the brace form — indirectly, via
the stated return shape, rather than by a sentence saying "no doubled braces".
That is adequate: a doubled-brace prompt cannot contain `{ ok, matches }`.
