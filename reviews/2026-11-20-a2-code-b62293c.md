## F1 — A refused bind leaves the goal doubly undriven (`agent.py:1593-1598` + `:683`)

**Severity: real.** This is the one the concurrency question displaced attention from.

The goal path holds the script before it starts the planner thread (`agent.py:683`, and the
same shape at `:886`):

```python
_goal_id = self._new_goal_id(sender, text)
self._begin_script_hold(_goal_id, text)      # hold taken HERE
```

`on_script` releases that hold **only on the success path** (`:1593-1598`):

```python
if not self._bind_planner_script(source):
    return False                              # returns WITHOUT releasing
...
self._end_script_hold(goal_id or None)        # success path only
return True
```

`plan_orchestrator` then interprets `False` as "run step 2", and its own comment states the
assumption plainly: *"the bind was refused but the steps did not run: the goal has no driver at
all"* (`test_l3_script_path.py:301-303`).

**Executed, refused-bind path, plan carrying a script, hold set as the live path sets it:**

```
bind failed -> steps executed: 1
status: complete | handed_to_script: None
hold after a refused bind: {'goal_id': 'chat:Steve:keep the furnace fed#1'}
```

So on a refused bind:

- the step list runs (plan closes `complete`), **and**
- the goal's hold is still set, and only `_end_script_hold(goal_id)` for *that* goal can clear
  it — no later hand-out path clears this goal's hold once the plan is done.

`_run_script_tick` consults exactly that hold at `agent.py:2947` and returns `SCRIPT_HELD`
before dispatching. Whether the bot is free afterwards depends on whether the post-plan chat
body reaches `_begin_script_hold` again (it replaces the holder, `:1348-1352`), and that chat
body's own `execute_task` call is outside this diff — I did not read it, so I am not claiming
permanent silence. What I do claim is the state this diff produces: **the refused-bind path
executes one driver while leaving a hold that blocks the other.** The refusal is exactly the
case the code treats as routine — a hand-written binding winning, or the dry tick failing —
and a planner script that fails its dry tick is the likely refusal in practice.

**Fix shape:** release the hold on refusal too, since the plan will drive the steps. That is
the one-line change, and it is why this is NOT YET rather than a design objection.

**Why no test caught it:** every hold test in `test_agent_script_branch.py` (`:636-808`) sets a
hold and then calls hold helpers or `_run_orchestrator`; the three `TestExactlyOneDriver` tests
call `execute_task` with no hold at all. The two halves are tested separately and never
together, which is the only place the defect lives.

## F2 — Requirement 2a.9's "exactly one driver" has no end-to-end test

`TestExactlyOneDriver` is a genuinely good unit test of the orchestrator branch: `dispatch`
captures whether phase 2 ran, and the three cases (script / no script / refused) each kill a
named mutant. But it stubs `on_script` with a lambda. The production closure — bind, then
release the hold, return True — is never executed against the orchestrator.

That is why F1 is invisible: the test that would have caught it replaces the exact function
that has the bug. The delta's requirement is about the *live* path; the test pins the
orchestrator's half of it only.

**Fix shape:** one test that builds a real `BotRunner` (as `test_agent_script_branch.py`
already does), begins a hold, and drives `_run_orchestrator`/`execute_task` with a stubbed
`call_plan` returning a plan that carries a script, for both bind outcomes. Assert on the
hold and on dispatch in the same test.

## F3 — `plan.status = "complete"` on handover contradicts the codebase's honest-finalize rule (`plan_orchestrator.py:353`)

The normal finalize is emphatic about this (`:410-421`):

> Honest finalize (fix: never report false success). […] Any subtask left in a non-complete
> terminal state makes the WHOLE plan failed, regardless of how the loop exited.

The handed-over path sets `plan.status = "complete"` while **every subtask is still
`pending`** — the collapsed step list never ran by design — and then logs
`plan_close(status="complete")`. The guard that would have caught this is skipped because the
early `return` precedes it.

I checked the three consumers. Two are unaffected and one is quietly affected:

- **Replay (`plan_memory.lookup`, `:243`):** safe. `lookup` resets `status` to `"executing"`
  and resets every subtask, and `_reusable` (`plan_memory.py:65-82`) requires every subtask to
  carry pre-baked `SKILL` directives. A handed-over plan has none, so it is never recorded
  (`record()` returns before indexing) and never replayed.
- **DPO (`build_dpo_dataset.py`):** safe from this, for a reason worth stating. Its
  `_satisfied` comes from a **joined `outcome` record** (`:71`), not from plan status. The
  script path executes no subtask, so no successful exec call exists to mark satisfied — the
  handed-over goal is skipped, not counted as a false win. No leak, no bad training pair.
- **Skill authoring (`skill_author.py:140`):** affected. It keys on
  `plan_close.status == "complete"` and pairs that with exec calls. The handed-over plan
  contributes a "complete" close with no exec records, so it is a **false positive for "this
  plan closed successfully"** in the mining set — harmless today (nothing joins) but it widens
  the success set for no reason.

**Fix shape:** either a distinct terminal status for handed-over goals, or `"failed"` is wrong
too — if the status set is fixed, set `plan.meta["unverified"] = True` and have
`skill_author` skip it. Cheapest correct thing: don't claim `"complete"`; the meta flag
already records the handover.

## F4 — On handover the step list is erased from `plan_store` (low)

`plan_store.write(plan)` at `:357` writes the plan but never calls `plan_store.archive(plan)`;
the normal finalize does both (`:425-426`). Because the handed-over plan's subtasks all remain
`pending`, the stored
record says every step is pending, and the archive copy (written later, on the same object)
says the same. A player asking the dashboard "which steps did I get?" sees a plan that claims
nothing ran — accurate — but with no record that the script *was* handed the goal in the step
list itself; the only trace is `meta["handed_to_script"]` plus one telemetry line.

Low severity: nothing consumes it wrongly today. Noted because the archive step is silently
skipped on this path, which is the kind of asymmetry a later reader mis-models.

## F5 — An empty `goal_id` means the handover never releases a hold (low, cross-reference)

`on_script` calls `_end_script_hold(goal_id or None)`, and `_end_script_hold` returns `False`
for a falsy id by design (`:1360-1378`). So for any run that owns no goal — the
spec-driven/order-worker spawn paths documented at `:1469` — a handed-over goal leaves no hold
to release and no bug. **This is correct**, but it means the release in `on_script` is
conditional on a path that the F2 test would need to exercise with a real `goal_id` to be
worth anything.

## The concurrency question (point 4) — answered

**The surviving test pins enough for what it claims; the build-outside-lock window does not
need its own requirement.** Reasons:

1. The three fields are read and written as one unit under `self._lock` on both sides
   (`:3210-3217`, `:3243-3252`). The latch prevents a tick from re-reading the pair mid-bind;
   the lock prevents a tick from *observing* a mixture. Both are real.
2. **The lock is not reentrant** (`threading.Lock()`, `:274`), and it is a *general* instance
   lock — it also guards `chat_history` (`:483`, `:3782`), `_findings` (`:1278`, `:1286`) and
   `_last_action_results` (`:3612`). So the builder's decision to release it before the build
   is not merely a performance choice, it is the thing that keeps `ScriptTick.__init__` from
   deadlocking if it ever touches any of those. I checked: the build section (`:3268` in the
   extracted tree) calls `script_tick.ScriptTick(api, self.name, source)` and nothing that
   takes `_lock`. So today it is safe either way, but the builder's instinct to not hold a
   non-reentrant general lock across a WASM instantiation is the right call and worth keeping.
3. The guarantee the code offers is therefore **"a tick never observes a half-applied bind"**,
   not **"a bind never lands during a build"**. The builder's v3 failed precisely because it
   asserted the second. The surviving third test asserts the first at the only point it can
   fail, and the second test pins the lock is held across the swap.

**On the surviving test's strength, one caveat:** `test_the_tick_reads_its_three_fields_as_one_observation`
(`:381`) does not interleave a concurrent thread. Its `InterleavingLock.__exit__` mutates the
three fields *after* releasing the lock, and then reads them again on the next call. It kills
the reader-lock mutant (I reproduced: removing the tick's `with self._lock` reddens it), but it
does so by exercising a **sequential** interleaving, not a genuine race. A mutant that removed
the lock and happened to keep the three reads adjacent with no intervening statement would
survive. That mutant is hard to write in Python without changing semantics, so this is a
footnote rather than a blocker — but "the mutant dies 3/3" is closer to "the mutant dies
against a deterministic replay" than "the mutant dies under concurrency". Say the weaker thing.

## What is good here, and worth not losing

- **The strip runs before `raw` is used at all** (`l3_planner.py:461`), between
  `_strip_codefence` and `json.loads`, exactly where the delta says. The script-free path
  returns the original text object unchanged, so byte-identity holds by construction rather
  than by re-serialisation luck. This was the DPO-leak finding's whole point and it is closed
  properly, not papered over.
- **The malformed-input case returns the original text**, so `call_plan`'s existing
  `JSONDecodeError` path still reports on real bytes instead of on a rewritten blob.
- **`Plan.to_dict()` enumerates fields explicitly** (`plan_schema.py:57`) rather than
  `asdict`, and the code comments say why — that in-memory-only guarantee is real, and the
  comment names the exact refactor (`asdict()`) that would break it. That is the right way to
  leave a trap.
- **Prompt wording** distinguishes repeating goals from one-shot goals with the time-word
  caveat, and the three prompt tests pin it.
