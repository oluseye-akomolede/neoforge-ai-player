## The compound-assignment tightening

I raised this as non-blocking and the builder fixed it anyway. My concern in fixing a
"refuse more" rule is the opposite failure — a legal compare now refused as an
assignment — so that is what I attacked:

**Writes, all refuse:** `=`, `+=`, `||=`, `??=`, `-=`, `<<=`.

**Legal compares, all accepted:** `look.queries == null`, `=== null`, `!= null`,
`!== null`, and a bare `var z = look.queries;`.

The mechanism is sound: the check reads the whole operator run before `=`, and
`==`/`===` fall through because their run never has a non-`=` before the `=` tested.
`!=` and `!==` are not in the operator set at all. No false refusal found in any form
I tried.

## Residual R-1 — an unterminated string still swallows the declaration silently

Low severity, **not** blocking, and I want to be precise about why:

```
source:  var s = "abc     <- unterminated string literal
         queries = [ ... ]
result:  parse_declared_queries -> []      (no error raised)
```

`_mask_comments` leaves string bodies intact (it is the string pass's job), so an
unclosed quote runs to EOF in `_strip_strings` and takes the declaration with it. The
code comment at `script_tick.py:1152` says a `DeclaredQueriesError` surfaces a script
as unrunnable "the same way an engine-level syntax error is" — but this path raises
nothing, so it takes the quiet branch rather than the loud one it is described as
matching.

**Why it does not block:** the script is invalid JavaScript. It cannot bind and run as
a silent zero-query script, because the dry tick rejects it at evaluation before it
can produce a tick. The declaration stage being silent here does not reach
production. It is a cosmetic inconsistency with the comment's own description, not a
hole in the feature.

If anyone touches this file again, the cheap fix is to have `_strip_strings` report an
unterminated literal so the declaration stage fails loudly, matching the comment.
