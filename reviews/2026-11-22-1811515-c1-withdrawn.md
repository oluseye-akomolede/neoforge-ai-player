## C-1: I was wrong, and here is the mechanism

My fake `kubectl` re-encoded the data field when it *rendered* the YAML after
`create`, so it produced a doubly-encoded document that the real CLI never
produces. Everything downstream of that fake inherited the error. The builder's
hypothesis was exactly right.

I could not use my fake to settle it — this VM has no `kubectl` binary (only my
own `/tmp` fixtures, which is the trap that fooled me). So I ran **their probe
verbatim against the real client on `controlplane`**, with `--dry-run=client`
and no namespace touched. Production was not involved and nothing was applied.

```
TOKEN_LEN=96
KUBECTL_RC=0
data:
  minecraft: 190946992920da9f511668b8e112d6aaa5bb9ee8973563a6ce94c456d1577ca6...
DATA_LEN=128
DECODED_BYTES=96
```

The 128-character field base64-decodes to **96 bytes**. `--from-file` writes
the *bytes it read*, and `-o yaml` renders those bytes encoded once; `apply`
decodes once on ingest. One encode, one decode, stored value = the token. My
claim that the stored value would be `base64(96 hex)` was wrong.

**The tell I should have caught in my own harness:** I asserted a 128-char
stored value and called it corruption, when 128 is precisely
`ceil(96/3)*4` — the only length a correct single encode can have. I read a
correct number as a symptom. That is a new instance of a failure mode I have hit
before: the fake encodes on one stage and again when it renders, and the result
looks exactly like the defect I was looking for.

## C-3 / the read-back: PASS, and I verified it reddens

The fingerprint now hashes `STORED`, read back from the cluster, and refuses on
mismatch. Three runs against a fake that **corrupts the write** (simulating
exactly the double-encode I had wrongly claimed was happening):

| Version | Against corrupting fake | rc | Fingerprint printed? |
|---|---|---|---|
| `63e7d92` (pre-fix) | created, reports success | 0 | yes, `sha256:ec8db772` — wrong value |
| **mutant E** (read-back comparison disabled) | created, reports success | 0 | yes, `sha256:4aa3d7c0` — wrong value |
| `1811515` (fixed) | **refuses**: "read-back mismatch: stored 128 chars, expected 96" | **1** | **no** |

Mutant E is the load-bearing check and it was applied behind
`assert old in s` with `bash -n` before the run, so a no-op parser error could
not read as survival. It shows the guard — not some other difference — is what
catches a bad write. The pre-fix script demonstrably could not.

Also confirmed at `1811515` against the faithful fake: a correct write stores
**96 characters**, and the fingerprint is computed from the read-back value, so
it now describes the artefact rather than the intention.

**Two absences, scoped:** zero occurrences of the token in any traced `kubectl`
argv (`bash -x`, `grep -c` → 0) and zero occurrences in any output line. The
mismatch message prints lengths only, never either value.

## Not established

No prod write. The 1811515 runs used fakes for `create`/`apply`/`get`; the only
real-client evidence is the `--dry-run=client` probe showing the encoding is
single. That is enough to withdraw C-1 and not enough to prove a real
`create`+`apply` round-trip in ns `minecraft`, which remains untested by design —
it is a prod write and belongs to the rollout, not to this review.

## Note for the rollout row

The script's contract is now sound, but the fingerprint evidence only becomes
meaningful *after* a real write, because it fingerprints the read-back. The
first real run should record `sha256:<8>` and that value should be reconciled
against a second read-back.
