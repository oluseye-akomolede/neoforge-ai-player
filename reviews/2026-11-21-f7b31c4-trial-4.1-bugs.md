## BUG 1 - the prompt's examples: confirmed, exactly as filed

SCRIPT_SURFACE (agent/planner.py:41-42 at the rev) offers, for api.do:

  `directive` is an exact name like `"goto"`, `"mine"`, `"attack"`, `"place"`.

Against the real constant, imported from action_binding:

  goto    -> GOTO    bound=True
  mine    -> MINE    bound=True
  attack  -> ATTACK  bound=False
  place   -> PLACE   bound=False

So the commit's claim - "attack and place, neither is in BINDABLE_KINDS" - is
correct and is the right pair to name. Two of the four examples work and two do
not, which means the prompt is not uniformly wrong; the model that copies
"attack" is refused and the model that copies "goto" is not. That is a worse
failure than an all-wrong list, because it looks like it works sometimes.

The upper-case claim is right: action_binding.py:74 does
`kind = raw.strip().upper()` before the membership test at :75, so `"mine"`,
`"Mine"` and `"MINE"` all bind. Stating that in the prompt is correct. The
counts check: AGENT_SIDE_KINDS 10 + MOD_DIRECTIVE_KINDS 35 = BINDABLE_KINDS 45.

The requirement's scenario is falsifiable as written ("every kind the prompt
names as a bare example is in the set"), and task 2a.13 adds the sharper
version (pass each example through bind_action and require no RefusedAction;
removing a kind from BINDABLE_KINDS without touching the prompt reds). Both
would have caught the current state.

## BUG 2 - the all-refused fall-through: confirmed, mechanism verified

Read at the rev:

  agent.py:3225-3230  `if not handled:` ... `return False` on the refusal path
  agent.py:3584       `if self._run_script_tick(): ... continue`
  agent.py:3588       `if not self._plan_steps: self._check_task_board()`
  agent.py:1810       _check_task_board is called ONLY from :3589

So the delta's chain holds exactly: a refused tick returns False, the caller
does not `continue`, `_plan_steps` still holds the reply that carried the
script (nothing clears it on this path), and _check_task_board is gated on that
list being empty. The planner is therefore never asked again and the identical
tick repeats. The requirement's description of the bug is accurate, including
that the log says "falling back to planner" while nothing falls back.

The two scenarios are the right pair: it must stop being the driver, and a
dispatching tick must reset the counter. The consecutive-counter clause is
what stops an intermittently-working script being torn down, and I would have
asked for it if it were absent - a script that refuses 8 ticks then dispatches
one is making progress, not stalling.

Option 1 (yield the goal) is chosen and justified in the text rather than left
open. That is fine for a spec delta, and task 2a.14 carries the same choice plus
a test for the reset.

## My own instrument error, caught before it became a finding

My first check of BINDABLE_KINDS was case-sensitive: `'attack' in k` returned
False for all four examples including goto and mine, and I was one step from
filing that "all four examples are wrong, the delta understates it". The
constant is upper-case and bind_action upper-cases the input; the correct test
is `raw.upper() in BINDABLE_KINDS`, which gives the split the delta describes.
I had read the :74 upper-case line and then not applied it to my own probe. The
delta's own text warns about exactly this, one paragraph above where I got it
wrong.
