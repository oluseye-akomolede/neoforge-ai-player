# NC-1 is owed now, not later: FOLLOW on a present player holds a goal forever

Row: `qitem-20261122045802-740b42e3250d56f9` (follow-up to my NC-1 on `7c92a43`).
Reviewer: minecraft-reviewer@minecraft. 2026-11-22.

**Verdict: the condition the builder wrote as "when it becomes owed" is already
true.** This is not a hypothetical for a future commit; the path exists on
`7c92a43` today and I drove it.

## The row's own test, applied

The row says: *"When it becomes owed: if FOLLOW against a PRESENT player can hold
a goal indefinitely, that path has no mod-side bound and the ACTIVE status
becomes a permanent stall."*

Both halves are true on the current tree.

**FOLLOW on a present player never goes terminal.**
`FollowBehavior.tick` (`FollowBehavior.java:93-110`) returns `RUNNING` for the
present-target cases by design — aboard steering `:93`, within `followDistance`
`:99`, teleport-approach `:104`, ground-follow after. The only terminal exits are
`OFFLINE_GIVEUP_TICKS` (400) on the target-missing branch `:67`, which by
construction requires the target to be *absent*. Against a present player there
is no tick bound. `MAX_TICKS` is `GotoBehavior`'s alone; `Behavior` is an
interface, so nothing is inherited.

**A script can issue it.** `action_binding.py:41` lists `FOLLOW` in the bindable
kinds and `:73` gives it a single required arg, `target`. So the chain is live
end to end: script issues `FOLLOW <present player>` → status stays `ACTIVE` → the
in-progress gate at `agent.py:3443` resets `_script_idle_run` every tick → the
bound at `:3462`/`:3348` can never be reached → the goal is held indefinitely.

## Driven, not argued

With an active goal and a directive that stays `ACTIVE`, through the suite's own
harness:

    ticks=1     orch=0 idle_run=0 plan=['follow master']
    ticks=10    orch=0 idle_run=0 plan=['follow master']
    ticks=1000  orch=0 idle_run=0 plan=['follow master']
    ticks=5000  orch=0 idle_run=0 plan=['follow master']

The planner is never called and the idle counter never leaves zero, at any
duration. At `TICK_DELAY = 2.0` (`config.py:103`), 5,000 ticks is about **2.8
hours** with no yield, and nothing in the code makes a later tick behave
differently from the 5,000th. This is the trial-4.2 symptom — a bot held on a
wait that cannot end — one layer up, at the mod's behaviour instead of the
script's poll.

## What I am not saying

Not that this commit is wrong. `7c92a43` fixed a real and more common defect,
and the trade it made was correct for the evidence then available: before it, a
working long FOLLOW was torn down every 5 ticks. This is me now supplying the
evidence that flips the other side of the trade from theoretical to
demonstrated, which is exactly what the row asked for.

Not that `SCRIPT_IDLE_MAX` should be weakened. My NC-1 said the same: the fix is
a third terminal condition, not a weaker in-progress gate.

## Suggested shape (theirs to decide)

A directive that has been `ACTIVE` longer than its behaviour's own expected bound
implies should count as stalled. Two cheap forms:

- An absolute cap: `SCRIPT_DIRECTIVE_MAX_TICKS` on consecutive `ACTIVE` ticks,
  set well above `GOTO_MAX_TICKS` (600) — e.g. 3,000 — so bounded behaviours
  never trip it and a genuine long FOLLOW simply gets re-planned eventually.
- Or per-type: `FOLLOW` gets its own long bound, since it is the one behaviour
  that is *meant* to run indefinitely and should be bounded by staleness rather
  than duration.

Either keeps the in-progress gate doing its job for walks while closing the
permanent stall.
