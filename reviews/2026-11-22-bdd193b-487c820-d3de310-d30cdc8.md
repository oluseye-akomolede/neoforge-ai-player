## F-1 (observation, no fix required): the test pins the thread, not `call_plan`

`test_a_yielded_goal_produces_exactly_one_new_plan_call` asserts
`self.a._run_orchestrator.call_count == 1` — it mocks `_run_orchestrator`
itself. The task's criterion says "a yielded chat goal produces exactly one new
`call_plan`". The test proves the re-plan *thread is started*, not that
`call_plan` is reached.

I drove the real path (see above): `execute_task` does reach `call_plan` once
with the right task, so the **code is correct**. But note `execute_task` has two
zero-LLM shortcuts before `call_plan` — `_manage_fusion_intercept` and
`plan_memory.lookup` / `_plan_from_skill`. A re-submitted goal matching a
remembered plan can be answered **without any `call_plan`**. My drive stubbed
those to `None` to reach `call_plan`; in production a repeated goal may well hit
plan-memory. So "exactly one new `call_plan`" is not guaranteed by the code as
written — it is guaranteed only when no shortcut intercepts.

Not a defect in this task (re-planning from plan-memory is still a re-plan), but
the requirement's wording and its test drift apart. Worth either narrowing the
requirement to "the goal is re-submitted to `execute_task`" or adding a test
that drives `execute_task` with the shortcuts live.
