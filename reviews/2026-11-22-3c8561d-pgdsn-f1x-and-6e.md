## 6e — CLOSED, and the six-outcome table reproduces

The `/dev/null` defect is gone. The query now runs inside the pod and its
*verdict is decided outside*, from the exit status, with `rc=0` distinguished
from `rc!=0` and a second inner `case` catching `rc=0` with a non-integer count.
`unknown` is reachable through two distinct paths, both intended.

I replayed the decision construct directly rather than accept the table, and all
six rows match the builder's exactly:

| out | rc | line |
|---|---|---|
| `2` | 0 | `ok: p authenticated, 2 bot(s) connected` |
| `0` | 0 | `fail: p reports no connected bots` |
| `garbage` | 0 | `unknown: ... rc=0 but no count` |
| `` | 0 | `unknown: ... rc=0 but no count` |
| `` | 3 | `unknown: ... (rc=3)` |
| `` | 1 | `unknown: ... (rc=1)` |

I also probed two cases not in their table, because a table whose every `rc!=0`
row has empty stdout does not exercise the capture:

- **Partial success** (`echo 2; exit 3`) — `out` survives the nonzero exit and
  the capture yields `out=[2] rc=3`, which lands on `unknown`. Correct: a query
  that printed something and then failed is not evidence of a healthy agent.
- **Empty port argument** — `kubectl ... | base64 -d || echo 5000` can yield an
  empty string if `base64 -d` succeeds with no output, making `sys.argv[1] == ""`.
  I ran the script with an empty arg: `urllib` raises, the script exits 3, and the
  verdict is `unknown`. A misread port degrades to the safe outcome and cannot
  manufacture a false `ok` or a false `fail`.

## The endpoint claims are true; two of the four line numbers are not

I checked the cited paths rather than trusting them. Every *claim* holds:

- `DASHBOARD_ENABLED` defaults to true and `DASHBOARD_PORT` defaults to 5000 —
  `agent/config.py:110`, not the cited `:116`.
- `/api/state` returns `shared_state.snapshot()` — `agent/dashboard/server.py:98`,
  as cited.
- `snapshot()` returns a `bots` **dict** — `agent/dashboard/state.py:56-62`, as cited.
- A bot entry carries `"status"`: the producer is
  `shared_state.push_bot_snapshot(self.name, {..., "status": status, ...})` at
  `agent/agent.py:2905`, and `state.py:31` stores it as `self._bots[name] = snapshot`.
  The cited `agent.py:4576` is **past end of file** — the file is 4512 lines.
- `/api/bots` returns `list(snap["bots"].keys())`, i.e. bare names, so the
  builder's reason for preferring `/api/state` is correct
  (`agent/dashboard/server.py:104-106`).

So the fix's reasoning is sound on every point that matters; two of the four
coordinates a reader would follow to check it are wrong. Correcting `config.py:116`
→ `:110` and `agent.py:4576` → `:2905` is a two-character-class edit.
