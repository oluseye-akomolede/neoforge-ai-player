## F1 (BLOCKING) — the requirement states both the old design and its refutation, 9 lines apart

`spec.md:336`:

> **The script rides as one extra OPTIONAL field on `call_plan`'s reply.**

`spec.md:342-351`:

> **The script MUST NOT appear in any field the DPO trainer reads** ... a script
> embedded in the reply JSON would therefore reach the trainer twice ... once
> through `parsed`, and once more through `response_raw`, which is the field DPO
> actually trains on.

`spec.md:352`:

> **So the script is not carried inside the reply's JSON at all.**

`:336` says the script is a field on the reply; `:352` says it is not carried in
the reply at all. These are not reconcilable by reading "field" loosely: `:336`
says "on `call_plan`'s reply", `call_plan` returns the parsed `Plan`, and the
same sentence requires that plan to be byte-identical to today's. A separate
top-level key is a different object, not a field on the reply.

An implementer reading the requirement top-down meets the old sentence first and
builds the design the next paragraph exists to rule out. The paragraph that
explains the leak has no force against a preceding MUST-shaped statement that
prescribes it.

**Fix:** delete or rewrite `:336` to match `:352` (e.g. "The script is carried
in a separate channel, never inside the reply's JSON"). One sentence.

## F2 (BLOCKING) — the implementing tasks still carry the design F1 forbids

`tasks.md:87-89` (task 2a.1):

> **The script is ONE extra optional field on `call_plan`'s reply** — not a new
> `kind`, not a new directive type. `Plan` gains an in-memory `script`

That is the `parsed`-only guard the builder's own message calls insufficient

retains the narrow guard; the requirement widened it to `response_raw`.

The task list is what the builder works down. A correctly-stated requirement
with a contradictory task produces the leak in code with a green spec beside it.

**Fix:** rewrite 2a.1 to the separate-channel design and 2a.3 to the
`response_raw`-inclusive wording, matching `spec.md:342-371`.

*(Dependency note, not a finding: 2a.3 defers to a dags-lead row on whether the

## F3 (BLOCKING) — "that earlier script also resumes" describes a path the code cannot take

`spec.md:510-513`:

> A script already bound from an earlier goal, or a hand-written one, is a rival
> to this goal and remains held for it exactly as today: binding the goal's own
> script releases the hold, and with it **that earlier script also resumes** —
> the goal is no longer planning, so there is nothing left to contend with.

`_bind_planner_script` **replaces** the source: `agent.py:3185`
`self._planner_script = source`. After a successful bind, the earlier script is
overwritten; it does not resume, it ceases to exist. The only thing that runs
next is the newly bound script.

The sentence's intent is sound — releasing a hold without a replacement bind
would let an old script resume, which is why the release must be part of the
bind. But as written it claims a behaviour the code rejects, and a test written
to it ("the pre-existing script's actions resume after the bind") cannot pass.

**Fix:** state what actually happens — the earlier script is replaced by the
bound script, and the hold release is safe *because* the bind replaces it.
Or, if a bound script from an earlier goal is meant to survive, say so
explicitly and change `:3185` — but then the two-actor hazard the one-driver
requirement exists to prevent returns, so I would not.

## F4 (MINOR) — the mechanism sentence names a function that does not exist

`spec.md:354-356`:

> The script travels in a channel separate from the JSON object the trainer
> consumes — either a distinct top-level key on the API response that
> **`_parse_plan`** strips before `json.loads`, or a second call.

`_parse_plan` does not exist in the tree: repo-wide
`grep -rn "_parse_plan" --include=*.py` returns zero hits; the only occurrences
anywhere are this spec line and this review quoting it. The actual parse is
`raw = _strip_codefence(answer_text(resp.json()))` at
`agent/l3_planner.py:427` then `data = json.loads(raw)` at `:429`, inline in
`call_plan` — no helper to hook.

Worse, the two options offered are not equivalent, and the first is harder than
its one-clause description: `resp` is Ollama's `/api/chat` with `format: "json"`,
so the reply *is* the model's text, `raw`. "Stripping a top-level key before
`json.loads`" therefore means rewriting `raw` — the same string logged as
`response_raw`. That works, but it is a real step and it needs the parser to
exist, which it does not.

**Fix:** name the actual insertion point (`call_plan`, `agent.py:428-429`), or
say "a helper this change introduces" rather than citing one that isn't there.
Keep the second-call option; it is genuinely simpler to reason about, and the
latency/cost trade the builder makes is a defensible choice I would not reverse.
