# 1e2a789: stop and failed hand-back unbind the planner script — PASS

Rev reviewed: `1e2a789`.
Reviewer: minecraft-reviewer@minecraft. 2026-11-22.

Both live defects the lead's TEST log showed are fixed: a failed script held at
`(cooldown)` forever paying a runner call and suppressing its own `say`, and a
`stop` that cancelled the orchestrator while the script kept ticking.

## The design decision is the right one

Two mechanisms, and they are correctly distinguished:

- **Planner script → unbind** through `_unbind_planner_script` itself, which
  refuses a hand-written script structurally (`_planner_script` is empty for
  one). So "a deployment is never erased" is a property of the callee, not a
  condition each caller must remember — the right way round.
- **Hand-written script → halt** (`_script_halted_for_stop`), because it cannot
  be unbound without erasing `bindings.json`. It is deliberately *not* a hold: a
  hold is owned by a goal and released when that goal ends, so a hold on a stop
  would wait for a release that never comes. The commit states this and the code
  matches it.

The halt is gated at `_get_script_tick`, the single place a `ScriptTick` is
materialised, so a halted script pays no runner call at all — which is precisely
the behaviour the lead measured as missing.

## Drives

Halt does not re-enter the idle machinery (the concern this branch's own earlier
fix raises). Positive control first, because a zero from a harness proves nothing
until it is shown the harness can reach the path:

    CLEAN CONTROL (quiet script, active goal, 30 ticks) yields= 6  idle_run= 0
    HALTED        (same fixture, halt set, 30 ticks)    yields= 0  idle_run= 0

The control reaches `_yield_script_to_planner` and climbs the counter; the halted
run yields nothing and never touches `_script_idle_run`, because `_get_script_tick`
returns `None` before any idle counting. A halted script is inert, not a slow
poll. Also confirmed a halted script cannot hand a result back at all
(`HALTED_TICK_IS_NONE = True`), so the halt and the failure hand-back are
mutually exclusive and cannot fight.

The halt lift covers every goal-accept path: `_begin_script_hold` has exactly two
callers (`agent.py:905`, `agent.py:1108`), both the L3 plan-accept paths. The
failed hand-back at `:1283` starts the orchestrator with the *existing* goal_id
rather than accepting a new goal, so it correctly does not need to lift.
