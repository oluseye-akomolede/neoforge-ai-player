# Review — sub-step (a2): the script output reaches the L3 goal path

**Verdict: NOT YET**
Rev: neoforge `daf8aee` (spec delta only: proposal.md, tasks.md, spec.md)
Reviewer: minecraft-reviewer. Date: 2026-11-20.

The design is right and the diagnosis is honest: step (a) was wired into
`planner.decompose`, deployed, and unreachable because goals go through
`l3_planner.call_plan`. Moving the script onto the L3 path is the correct fix,
and "one optional field on the reply, not a new kind" is the right shape.

Two findings block. Both are the same species: the delta states a guarantee the
code's actual data flow cannot support, in the one place where an implementer
would trust it and stop checking.

## F1 (BLOCKING) — the DPO leak guard names the wrong field; `response_raw` is the one the trainer reads

The requirement says:

> With no script present the planner's reply, the resulting `Plan`, and the plan
> record written by `trajectory_log.log_call` MUST be byte-identical ... a
> trainer reading `prompt_system`, `prompt_user`, `response_raw`, `parsed`, or
> `world_state_summary` sees exactly what it sees now. The script field is
> additive on the reply and MUST NOT be copied into the parsed plan object.

The last sentence protects `parsed`. The DPO export does not read `parsed`.

`agent/build_dpo_dataset.py:89-93`:

```python
if win["_satisfied"] and win.get("response_raw"):
    pairs.append({
        "prompt": win.get("prompt_user", ""),
        "chosen": win.get("response_raw", ""),
        "rejected": fail.get("response_raw", ""),
```

`chosen` and `rejected` are the **verbatim `response_raw`** of the call — the
whole reply string L3 returned, script field and all. And `call_plan` logs that
string directly:

- `l3_planner.py:466-471` — `trajectory_log.log_call(..., response_raw=raw, parsed=data)`. `raw` is the full model reply; `data` is `json.loads(raw)`.
- `trajectory_log.py:90-91` — both `response_raw` and `parsed` are written to the record.

So a script in the reply leaks **twice**: through `parsed` (which the
requirement at least names) and through `response_raw` (which it does not).
An implementer who reads "MUST NOT be copied into the parsed plan object",
strips the script from the dict, and passes the check would still ship the leak
in `response_raw` — and `response_raw` is what trains.

The consequence is not cosmetic. Every future DPO pair would contain a script
in `chosen`, i.e. the fine-tune would be taught to emit scripts as part of its
planning JSON. `proposal.md` repeats the over-claim at section 3: "The script is
kept out of the parsed record `trajectory_log` writes, so the DPO export sees no
new field." That sentence is false as written.

`tasks.md 2a.3` half-sees this — it says the export "may read `call_plan`
prompts and **replies**" — but then scopes the mitigation to `parsed` only.

**What the requirement must say**, one of:

(a) the script is stripped from the reply **text** before `log_call` (so
`response_raw` is the plan-only JSON), or
(b) `response_raw` is allowed to carry the script and the DPO export is
changed to not train on it — which needs a scenario and a task, and contradicts
"sees exactly what it sees now".

(a) is smaller and keeps the trainer claim true. Either way the sentence
"a trainer reading ... `response_raw` ... sees exactly what it sees now" must be
made true or deleted; right now it is the opposite of the code path.

Scenario needed: **GIVEN** a reply carrying both a plan and a script, **WHEN**
the call is logged, **THEN** `response_raw` and `parsed` both contain no script
source. That is testable against `log_call`'s output and would have caught this.

## F2 (BLOCKING) — "ownership, not timing" is implementable, but the delta omits the synchronisation that makes it safe

Attack 3 was flagged as a risk by the builder; it is a real gap.

The hold is keyed correctly: `_begin_script_hold(goal_id, text)` at `agent.py:683`
records `_script_hold` carrying `goal_id`, and `_run_script_tick` returns
`SCRIPT_HELD` at `:2927-2930` when a hold exists. So "a script bound FOR goal G is
not held by G" is expressible as a comparison — `hold['goal_id'] == bound_script_goal_id`
— without ending or reassigning the hold. That part is fine, and the requirement
is implementable as phrased.

What the delta does not say:

- `_bind_planner_script` (`agent.py:3149`) mutates `_planner_script`,
  `_script_loaded` and `_script_tick`, and runs a dry tick, with **no lock**.
- `_run_script_tick()` is called from `_loop` (`agent.py:3252`, call at `:3274`)
  with **no lock** held — verified: zero `with self._lock` between `:3240` and
  `:3274`.
- The orchestrator binds from the `orch:<bot>` thread.

The requirement *requires* these to overlap: "binds it ... before the bot's own
tick would run it" and "dispatches its actions while the goal is still running".
So the bind and the tick read/write the same three fields from two threads with
no synchronisation, and the spec says nothing about it. `self._lock` exists and is
used elsewhere (`:483`, `:1278`, `:3454`), so the mechanism is present; the
requirement just doesn't ask for it.

This is a spec gap, not a code bug — there is no code yet. But it is exactly the
kind of omission that ships a rare, unreproducible double-dispatch: the window is
between `_get_script_tick()`'s latch check and its `return`, and between the bind's
assignment and its latch reset.

**What the delta needs:** the bind and the hold-ownership read MUST be atomic with
respect to the script tick (state it as a requirement or a named task), plus a
scenario that exercises a bind concurrent with a running tick.

## Verdict

NOT YET. F1 is a wrong-field guarantee that would train future models on scripts
and is cheap to fix (one clause + one scenario). F2 is a missing atomicity
requirement for code that does not exist yet, so fixing it in the spec now costs
nothing and fixing it after the build costs a flaky race hunt.

Everything else in the delta is accurate and implementable.
