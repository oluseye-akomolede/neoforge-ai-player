## The blocker (one stale line number, two sites)

**Spec `:356` and `tasks.md:91` cite `l3_planner.py:427` for the expression
`raw = _strip_codefence(answer_text(resp.json()))`.**

At `836e2ae` that expression is on **`:426`**. `:427` is `created_at =
datetime.datetime.utcnow().isoformat()`.

Verified by content, not by number:

```
425:    resp.raise_for_status()
426:    raw = _strip_codefence(answer_text(resp.json()))   <-- the quoted expression
427:    created_at = datetime.datetime.utcnow().isoformat()
428:    try:
429:        data = json.loads(raw)                          <-- correctly cited
```

### Why this is not cosmetic

Both sites use `:427` as the **lower bound of the insertion point** for the strip helper:

- `spec:356` — "…called **between those two lines**" (`:427` and `:429`)
- `tasks.md:91` — "between `l3_planner.py:427` and `:429`"

`raw` is assigned at `:426`, not `:427`. The "between those two lines" instruction
therefore brackets the **wrong span**: it starts *after* the model text is already bound to
the name that is logged verbatim as `response_raw`. A careful implementer can still call
the helper at `:428` and pass `raw` in — so this is not unimplementable — but the number
tells them the text is bound at `:427`, and the paragraph's own warning is that cleaning
must happen "BEFORE it is logged, not filter afterwards." The pointer is the input to that
decision, and it is off by one.

So at these two sites the citation contradicts the instruction it annotates. Following the
prose avoids the leak; following the number does not guarantee it.

**Fix:** `427` → `426` at `spec:356` and `tasks.md:91`. The `:429` cites are correct as
written. Nothing else in this finding.

## Design: PASSES

All four findings from `fe5c6bd` are answered, and two are answered better than I filed them.

**F1 (DPO leak).** The requirement now names `response_raw` explicitly and states the
constraint as "nowhere," with both scenarios I asked for: no trainer-read field contains
script source, and `chosen` is byte-identical to the same plan without a script. The
strip-before-parse channel is the right choice over a second planner call — one
deterministic split, `response_raw` clean by construction, no second reply that can
disagree with the first. **I endorse this; no design objection.** The delta deliberately
does not depend on the dags-lead row (`qitem-20261120145614-…`) being answered, which
holds whichever way that lands.

**F2 (atomicity).** Written as a guarantee, not a primitive — lock, atomic swap, or single
object replacement all satisfy it. That is correct spec altitude and does not pre-empt the
implementation review.

**F3 (replace-not-resume).** The builder kept my sentence and added the part that makes it
coherent: the release is safe *because* the bind replaces the rival, plus the hand-written
case broken out separately. Better than what I filed.

**F4 (`_parse_plan` invented).** Correctly replaced with the real inline parse and the
log-before-filter consequence.

### The two remaining "resumes" hits are correct — checked, not assumed

The builder flagged `spec:323` and `proposal:26` and left them. Both are in a *different*
discriminator than the bind-replaces passage:

- `proposal:26` — describes the **existing M3-1g rule** (a chat command holds a running
  script; the script resumes with its remembered value). Ordinary hold lifecycle.
- `spec:322-323` — a scenario about what happens **when the held goal ends**.
  "Resume" there is end-of-goal release, not a bind during a goal.

Neither contradicts `spec:522` ("replaced, not resumed"). The discrimination is real and
both are right as written.
