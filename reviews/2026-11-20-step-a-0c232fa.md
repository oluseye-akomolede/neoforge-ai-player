so every caller pattern is unchanged. Probed at the rev: `isinstance(r, list)` is
True; `len`, iteration, `r[0]`, `r[-1]`, `== ["a","b"]`, `json.dumps`, and the
`", ".join(f"{i+1}. {s}" for ...)` shape agent.py uses for `step_list` all behave
exactly as a plain list. `_script_from` returns None for a non-dict, for
`{"script": ["not","str"]}`, and for a steps-only answer. The `__new__` fixtures
work because `_get_script_tick` reads `_planner_script` via `getattr`.

**Attack (2), order — holds.** Three mutants, run individually against the clean
rev:

  `test_a_failed_dry_tick_binds_nothing`.

  **reddens** `test_a_planner_script_does_not_displace_a_hand_written_one`.

  `dry.called` is **False**, so the ordering is pinned, not just the outcome.

**Attack (3), citations — the latch addresses are right; two others are not.**
At `0c232fa`: `:235` is `self._script_loaded = False`; `:3206` is
`if self._script_loaded:`; `:3207` is `return self._script_tick`; `:3208` is
`self._script_loaded = True`; `:2909` is the single `self._get_script_tick()`
call. The `0c232fa` repair moved these from the stale `3204-3206` form correctly.
The reset itself is `:3183`, inside `_bind_planner_script`.

The latch has three writers (`:235` init, `:3183` reset, `:3208` latch-set). The
spec's "only writer" claim is about the **reset**, and no other code path clears
it — that invariant holds.

## F1 (blocking) — the latch reset has no test; the mutant survives all 314

`tasks.md` 2.4 is ticked and the spec makes the reset a MUST ("MUST gain a defined
reset ... MUST be its only writer"). The code does it. **Nothing proves it.**

Mutant: delete the two reset lines from `_bind_planner_script`
(`self._script_tick = None` / `self._script_loaded = False`), leaving the
assignment. Result: **all 314 tests pass**, same 30 failures + 1 error as the clean
rev, zero new reds.

It survives because the one test that looks like it covers this —
`test_a_planner_script_is_bound_in_memory:1049`,
`assertFalse(self.a._script_loaded)` — is **vacuously true**: `setUp` already sets
`_script_loaded = False`, so the assertion cannot distinguish a reset from no-op.
The tests never bind twice, and never bind from an already-latched bot.

Run non-vacuously (agent latched from a prior build, `_script_loaded=True`,
`_script_tick="OLD-CACHED-TICK"`), the mutant gives:

```
bind returned      : True
_script_loaded now : True
_script_tick now   : OLD-CACHED-TICK
```

`_bind_planner_script` reports it adopted the script, while the bot keeps
executing the **previous** script for the rest of the process — which is exactly
the failure the requirement exists to prevent ("calls the existing path to 'bind'
... gets the PREVIOUS script for the life of the process"). Clean code gives
`_script_loaded: False`, `_script_tick: None`.

**Fix:** a test that latches the bot first (`_script_loaded = True`,
`_script_tick` = a stub), binds a new script, and asserts the old tick is cleared
and the next `_get_script_tick()` builds from the new source. Without a prior
latch there is no behaviour to observe.

## F2 (should fix) — the taskboard planning path drops a script silently

`agent.py:1702` is the second `planner.decompose` caller (the task-board task
path). It has no script handling, unlike `:904`. A script answer there is a
`PlannerResult([], script=...)`, so `steps` is empty: the bot sets
`_plan_steps = []`, logs `Plan (0 steps)`, and does nothing. The planner wrote a
program and it is discarded with no message.

Reachable: a claimed task with no pre-set `plan_steps` takes this branch
(`:1692-1702`).

The spec's scenario is general — "WHEN the planner plans the goal / THEN the plan
MAY be a script, and if it is, the script is validated and bound". A task-board
task is a goal. Either that path honours a script, or the spec says which planning
paths are out of scope for step (a). Silently doing nothing is the one reading the
spec's own "don't turn a quiet script into a dead bot" language argues against.

## F3 (fix before merge) — two stale citations

Both checked at `0c232fa`:

- `spec.md:244` cites `agent.py:1330-1333` for "the hold records a `goal_id`".
  Those lines are a docstring about goal ownership. `goal_id` is **recorded** at
  `:1349-1352` (`self._script_hold = {"goal_id": goal_id, ...}`).
- `spec.md:244` cites `:2901-2904` for "suppresses the BOT's dispatch". Those
  lines are docstring about the falsy return. The hold **suppresses** at
  `:2920-2922` (`hold = getattr(self, "_script_hold", None)` → `return SCRIPT_HELD`).

The `0c232fa` repair swept the latch addresses but not these two, in the same
document. Same class as the previous two rounds: citations inside prose that was
also rewritten.
