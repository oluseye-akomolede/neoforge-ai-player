## The checks the handoff asked for

### (1) A `done_reason=length` reply is no-script before extraction — HOLDS

`call_script` resolves `raw = answer_text(body)`, then raises `TruncatedAnswer`
on `body.get("done_reason") == "length"` **before** `extract_script_block` is
called (`l3_planner.py:1492-1501`). The raise lands in the existing
`except TruncatedAnswer` handler, which returns `None` at `:1507` — so a
length-stopped reply cannot reach the dry gate or the bind.

**My `''` mutant is dead.** Removing the guard reds
`test_a_length_stop_yields_no_script_even_though_a_block_closed`. Removing the
guard *and* the extractor is not a reachable mutant: the block is still extracted
into a local that is never returned.

The test that makes it non-vacuous is the right one:
`test_the_block_that_closed_is_one_extraction_would_have_returned`
(`test_l3_script_path.py:1071-1076`) asserts the *premise* — that the fixed
reply really does extract a script without the guard — so the pass above cannot
be passing because extraction rejected it for an unrelated reason.

The `''`-empty-block row is covered by `test_an_empty_block_is_no_script`

### (3) `_SCRIPT_NUM_PREDICT = 6144` on the SCRIPT call only, no `num_ctx` — HOLDS

All eight `num_predict` sites read at the rev: `491` plan 1024, `868` 400,
`918` 24, `970` 200, `1006` 768, `1102` 384, `1216` 768, `1478` the SCRIPT call
via the constant. Only the last moved. `grep -n "num_ctx"` over `l3_planner.py`
returns nothing — no `num_ctx` is sent, as decided.

I do **not** dispute the window decision and I did not probe the model: the
2048 figure came from my read of `/api/ps` after the builder's earlier `num_ctx`
probe had reloaded the model, and the lead's `OLLAMA_CONTEXT_LENGTH=114688`
supersedes it. Recording the correction because it changes what 4096 would have
meant: with a 2048 window, a 4096 budget could not be spent. With 114688 it can.

Log-only, not filed as a finding in its own right (M-1, editorial): the comment
block above the constant (`:1278-1283`) still reads "**4096** leaves room to
finish", which is now false of the value below it. The rule it states (6144 fits
inside `_OLLAMA_TIMEOUT`) holds — 6144 at 32–37 tok/s is ≈166–192 s of decode
plus a ≤68 s cold load, under the 420 s timeout — but the number in the sentence
should be 6144, and the reason is worth keeping: 6144 + prefill is what the
window now has to hold.
