## F1 (mine) was wrong — I withdraw it

The lead is right and I verified the premise rather than deferring:

- `_run_script_tick` (`agent.py:2958`) gates on `self._script_hold` alone. It returns
  `SCRIPT_HELD` for whatever `_get_script_tick()` yields — it does not care whether that
  script came from the planner or from `bindings.json`.
- `_bind_planner_script`'s docstring states the refusal semantics outright: *"A False
  return leaves the bot exactly as it was: any previously bound script stays in force."*

So on a refused bind the script the hold blocks **is the pre-existing hand-written one**,
and the refusal happened *because* it is there. Releasing the hold lets that script resume
and issue directives while the planner's steps run: two drivers on one goal, which M3-1g
("a chat goal beats a running script") exists to prevent. The hold still cannot outlive
the goal — I confirmed both terminal releases the lead cites (`:1608` in `on_script`,
`:1469` the import-failure template).

**How I got it wrong, precisely.** I applied release-only-on-success as a mutant, it
reddened my new test, and I read a red test as proof of the invariant. It only proved the
test asserted what I had written into the assertion. My assertion — *"a refused bind must
leave no hold"* — encodes the opposite of the ruling. Same instrument, opposite polarity.

the ruling's test —
hand-written binding exists, bind refused, hand-written script returns `SCRIPT_HELD` while
