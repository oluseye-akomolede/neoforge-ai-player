**Revs:** code `4211b2d`, docs `8d2602d` (tip), spec delta `a726530` — reviewed at `8d2602d`
**Supersedes:** `0784ce8` (single-call, `format:"json"` dropped on the plan call) — withdrawn by the lead after the 2a.9 trial; that row was closed `superseded`
**Verdict:** **PASS** — both named attack surfaces probed by execution; two count corrections; no blocking finding.

## Attack surface (1): the step-list path is genuinely unchanged — CONFIRMED

Driven, not read. With a `wants_script=false` reply, recording every transport call:

```
step-list goal: calls=1  format="json"  response_raw=verbatim plan  script=None
scripted  goal: calls=2  second call has NO format key
                script in plan.script only; response_raw contains no script source
```

`call_plan` (`l3_planner.py:462`) still sends `"format": "json"` on the plan call, and
`response_raw=raw` at `:521`/`:540` captures the plan reply before any script machinery runs. The
second call (`call_script`, `:1309`) fires only under `if data.get("wants_script") is True:`
(`:555`) and is **never logged** — `call_script` has no `log_call`. So the DPO leak I flagged when the lead was choosing a
design is structurally impossible here: `build_dpo_dataset.py:89-93` trains on `response_raw`, and
no script source ever reaches that field on either path.

A step-list goal makes exactly one call. Confirmed by mutant: removing the `wants_script` gate
reddens exactly the three step-list tests (`test_wants_script_absent_or_false_makes_one_call`,
`test...non_json...`, `test...logged verbatim...`), and nothing else. Restored, 25/25 green.

## Attack surface (2): can `call_script` fail a goal? — NOT at any reachable input

`call_script` catches `(requests.RequestException, ValueError)` around the `post` and
`TruncatedAnswer` around `answer_text`. I went looking for a raise that escapes, as asked.

| Path | Result |
|---|---|
| Network/HTTP failure | `RequestException` — caught |
| Non-JSON / bad-JSON body | `ValueError` from `resp.json()` — caught |
| Truncated answer | `TruncatedAnswer` — caught |
| `body` not a dict | `answer_text` guards with `isinstance` — returns `""` |
| `resp.json()` returns a list | `answer_text` guards — returns `""` |
| `_SCRIPT_SYSTEM_PROMPT.format(...)` (`:1325`) | 3 braces, all three fields — no `KeyError`; called, returns clean |
| `json.dumps({...})` (`:1327`) | `plan`/`summary`/`world_state` are JSON-native — no `TypeError` |
| `extract_script_block` (`:1356`) | regex over `str`, total — cannot raise |

**One hardening note, not a defect.** `TypeError` is not in `call_script`'s catch and is not a
`RequestException`; if a non-serialisable value ever reached the `json=` body, `requests`' own
encoding would raise it and it would escape into `call_plan`, failing the goal. Every value at this
call site is JSON-native today, so I could not construct a reachable input — this is a robustness
gap to close if the call site's inputs ever widen, **not** a live way to fail a goal. I am
explicitly not claiming a reachable path: I tried and did not find one.

Every failure mode of the second call leaves the plan intact — 1 subtask, `script` unset, no
exception past `call_plan`. The spec's central promise ("a script problem costs the script only")
holds under execution.

## The chain is wired end to end

`plan_orchestrator.py:255` calls `call_plan` → `l3_planner.py:564` sets `plan.script` → `:337`
`getattr(plan, "script", None)` → `on_script(plan, script)` → `agent.py` bind path. I initially
grepped for the literal `plan.script` and found nothing, and nearly filed "the script is set and
never read". The consumer uses `getattr(plan, "script", ...)`, which my query could not match. That
was a broken instrument, not a defect — noted here because the same miss would look like a finding
to a reader who did not re-query.

`Plan.to_dict` (`plan_schema.py:57`) enumerates fields explicitly, so the script is not persisted —
verified, and the code comment at `l3_planner.py:559-562` is accurate — including its own warning
that the guarantee rests on that enumeration and breaks if `to_dict` ever switches to `asdict()`.

## Design: accepted

The plan call keeps its shape and its JSON mode; `wants_script` is one optional boolean; the second
call is non-JSON and returns only a fenced block. That is a better trade than `0784ce8` for the
reason the lead gave — the common step-list path is not taxed for the rare scripted one — and it
removes the strip-before-parse hazard entirely rather than mitigating it. Not persisted in
`to_dict`, correctly: the script is memory state, and a resumed goal should re-plan rather than
replay a stale program.
